# ADR-001: Сага с локальными подтверждениями и компенсацией

**Контекст:** у Catalog и Reservations независимые H2.
XA/2PC с координатором глобальных транзакций не используется.

**Решение:** сначала коммитим `PENDING` с UUID `requestId` в Reservations,
потом `hold(bookingId, roomId, [start,end))` в Catalog, затем коммитим `CONFIRMED`.
При недоступности/неопределённом ответе отменяем бронь локально и отправляем
идемпотентный `release`. При сбое release сохраняем `compensationPending`, чтобы
отдельный планировщик повторил запрос. Это **синхронная сага с компенсацией**, а
не атомарная транзакция между двумя СУБД.

В Catalog вставка слота происходит в транзакции с блокировкой строки номера;
в записи о слоте `bookingId` служит ключом идемпотентности. На раннюю отмену без
созданного слота записываем tombstone `RELEASED`: запоздалый hold не сможет занять
комнату после компенсации. Пересечение интервалов: `a.start < b.end AND a.end > b.start`.

**Последствия:** операция может временно показывать `CANCELLED` вместе с
`compensationPending=true`. Без доступной долговечной БД после рестарта
сохраняемость гарантий отсутствует. Автовыбор пытается следующую комнату только после определённого ответа 409:
после тайм-аута исход неопределён и сначала обязательна компенсация.
